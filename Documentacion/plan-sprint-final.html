Reglas de pedido/OP + ajustes UI · Rama enmanuel · Auditoría 2026-06-08

Contexto

Implementación de los puntos [-] / [ ] del backlog auditado, con las reglas de negocio confirmadas:
Formalización: abono ≥ 70% del total formaliza el pedido y habilita producción.
Entrega: fecha del abono del 70% + 30 días hábiles (lun-vie, sin feriados).
Tras formalizar: se congelan tallas/cantidades/diseño; los pagos siguen editables (saldo 30% a la entrega).
Inventario en OP: el stock se descuenta al crear la OP. Si falta stock → se bloquea la creación (422).
Cancelación de OP (merma textil), condicional al estatus:
  • Pendiente → tela sin cortar → repone stock (MovimientoInsumo Entrada).
  • En Proceso/Finalizado → tela cortada → no repone (merma) + exige motivo_cancelacion.

A Formalización 70% + entrega + bloqueo de líneas

Punto de enganche: PedidoService::syncPagos() — único lugar donde se materializan pagos y se llama recalcularAbono() (en crear() y actualizar()).

  1. Config — config/pedidos.php: abono_minimo_porcentaje 50 → 70.
  2. Migración — agregar fecha_formalizacion (DATE, nullable) a pedido (+ $fillable/$casts).
  3. Modelo Pedido:
    • estaFormalizado() → fecha_formalizacion no nula (flag sticky).
    • marcarFormalizacionSiCorresponde() → si cumpleAbonoMinimo() y aún no formalizado: setea fecha_formalizacion = hoy y fecha_entrega_estimada = Carbon::parse(hoy)->addWeekdays(30) (reutiliza addWeekdays(), que salta sáb/dom).
    • lineasBloqueadas() → estaFormalizado() || tieneProduccionActiva() || estado==='Completado'.
  4. PedidoService: en syncPagos() llamar marcarFormalizacionSiCorresponde(); nuevo actualizarSoloPagos() (solo pagos).
  5. Bloqueo de líneas con pagos abiertos — PedidoController::update():
    • Cancelado → bloqueado total.
    • lineasBloqueadas() → actualizarSoloPagos(); 422 anti-tampering si el payload de productos difiere de lo guardado.
    • Caso normal → actualizar().
    • Esto relaja el bloqueo total actual por producción activa, para poder registrar el 30% a la entrega.
  6. Front pedidos (pedidos/modals.blade.php, scripts/main.blade.php): exponer lineas_bloqueadas/fecha_formalizacion en show(); deshabilitar campos de líneas + banner "Pedido formalizado"; mantener paso de pagos activo; mostrar fechas.

B Inventario en OP (descuento + reposición condicional + merma)

Reutiliza el patrón de CompraService::procesar()/anular() (lockForUpdate() + MovimientoInsumo + transacción). Solo mueven stock los insumos con is_inventoriable = true.

  1. Migración — agregar motivo_cancelacion (TEXT, nullable) a orden_produccion (+ $fillable).
  2. Servicio nuevo ProduccionInventarioService:
    • validarYDescontar() — pre-valida stock (insuficiente → InvalidArgumentException con faltantes → 422); descuenta + MovimientoInsumo Salida; pivot cantidad_utilizada = cantidad_estimada.
    • reponer() — suma cantidad_estimada + MovimientoInsumo Entrada (motivo "Reposición por cancelación OP #id").
  3. OrdenProduccionController:
    • store() / storeBatch(): llamar validarYDescontar() dentro de la transacción (envolver store() en DB::transaction). Falla → 422, no se crea nada.
    • Endpoint dedicado de cancelación PATCH ordenes/{orden}/cancelar:
      • Pendiente → reponer(); motivo opcional.
      • En Proceso/Finalizado → no repone; motivo_cancelacion required.
      • Setea estado='Cancelado' + recalcularEstado() del pedido.
    • Quitar Cancelado de las opciones de update() (cancelación ya no pasa por el form).
    • destroy() (solo Pendiente): reponer() antes de borrar.
    • Insumos read-only al editar: update() deja de re-sincronizar insumos (stock ya comprometido). Corregir insumos = cancelar + recrear.
  4. Front órdenes (ordenes/modals/*, scripts/main.blade.php): botón "Cancelar orden" → modal que exige motivo si En Proceso+; manejar 422 de stock insuficiente con SweetAlert; lista de insumos en modo lectura.

C Filtros <select> máx 4 ítems + scroll

Los filtros usan <select class="form-select navy-filter-select"> nativo (su dropdown no acepta max-height por CSS). No se usa Tailwind/Alpine (stack = Bootstrap 5 + jQuery).

  • IIFE global en layouts/app.blade.php (patrón AtlanticoGuard) que realza cada select.navy-filter-select a un dropdown Bootstrap, manteniendo el <select> oculto como fuente de verdad (el JS de filtros existente sigue funcionando).
  • CSS en custom.css: menú con max-height ≈ 4 ítems + overflow-y:auto.
  • Solo select.navy-filter-select (excluye los input[type=date]). Aplica a todos los módulos automáticamente.

D Vistas de detalle: wizard → tabs

Convertir las vistas de lectura ("Ver/Detalle") que hoy usan stepper secuencial (wiz-stepper + Anterior/Siguiente) a tabs Bootstrap (nav-tabs + tab-pane). Los wizards de creación/edición se mantienen.

  • Confirmado: ordenes/modals/view.blade.php (Orden/Insumos/Progreso) + su JS en ordenes/scripts/main.blade.php.
  • Revisar y convertir, si son de lectura: "Ver detalle" de pedidos, cotizaciones y compras.
  • Patrón: reemplazar stepper por nav-tabs, eliminar navegación secuencial y su JS, conservar el contenido de cada paso como pane.

Verificación end-to-end
